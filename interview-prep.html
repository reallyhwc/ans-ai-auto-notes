1 如何判定一棵二叉树是不是满二叉树

核心：递归判断 — 左右子树都是满二叉树 + 左右子树高度相等。

定义澄清（面试第一件事）

术语中文定义节点数
Full Binary Tree完满二叉树每个节点有 0 或 2 个孩子无固定公式
Perfect Binary Tree满/完美二叉树每层全满，叶子同层2^h − 1
Complete Binary Tree完全二叉树除最后一层外全满 + 左对齐无固定公式

解法一：递归（推荐）

// Go — 返回 (高度, 是否满二叉树)
func checkFull(node *TreeNode) (int, bool) {
    if node == nil {
        return 0, true
    }
    leftH, leftFull := checkFull(node.Left)
    rightH, rightFull := checkFull(node.Right)
    return max(leftH, rightH) + 1,
           leftFull && rightFull && leftH == rightH
}

func isFullTree(root *TreeNode) bool {
    _, ok := checkFull(root)
    return ok
}
// Java 版本
class Result {
    int height; boolean isFull;
    Result(int h, boolean f) { height = h; isFull = f; }
}

Result checkFull(TreeNode node) {
    if (node == null) return new Result(0, true);
    Result left = checkFull(node.left);
    Result right = checkFull(node.right);
    return new Result(
        Math.max(left.height, right.height) + 1,
        left.isFull && right.isFull && left.height == right.height
    );
}

解法二：计数法（有坑！）

// ⚠️ 节点数 = 2^h - 1 只是必要条件，不是充分条件！
// 反例：
//     1
//    / \
//   2   3
//  / \   \
// 4   5   7
// 节点数 7 = 2³-1 ✓  但节点3只有右孩子 → 不是满二叉树 ✗

各环节防丢机制

环节丢消息场景防护机制
生产端网络超时消息未到 Broker同步发送 + 自动重试 2 次
存储端-刷盘机器断电 Page Cache 丢数据同步刷盘：每条 force() 到磁盘才回 ACK
存储端-复制Master 宕机 Slave 数据不全同步复制：等 Slave 确认写入后才回 Producer ACK
消费端Consumer 宕机没处理完消费确认 + 16 次递增重试 → 死信队列兜底
分布式事务本地事务成功但消息未投递Half Message + 回查机制 + 事务记录表

生产环境推荐配置

异步刷盘 + 同步复制 (SYNC_MASTER)
→ 兼顾吞吐和安全
→ 同步刷盘太慢（受限于磁盘 IOPS）
→ 但有 Slave 实时同步兜底，Master 宕了 Slave 有全量数据

面试应答要点

  • 不要只说"同步刷盘"一个点 — 可靠性是多环节组合
  • 提事务消息是亮点（Half Message + 回查，解决"本地事务和消息发送的原子性"）
  • 消费端重试 + 死信队列体现了最终一致性思想

3 MySQL B+ 树的实现原理

核心：B+ 树是为磁盘 I/O 优化的多路平衡搜索树 — 一个节点 16KB 存 ~1170 个 key，3 层能管 2000 万行，数据只在叶子 + 叶子双向链表。

为什么是 B+ 树？递进推演

数据结构单次 I/O 读什么问题
二叉搜索树一个 key + 两个指针 ≈ 16B一次 16KB I/O 只用 16B → 浪费 99.9%；千万行 ~23 层 → 23 次 I/O
哈希索引一个 bucketO(1) 等值完美，但不支持范围查询
跳表一个节点一个值为内存设计，磁盘上跨页 = 大量随机 I/O
B+ 树一页 16KB 塞满 key一次 I/O 过滤几百倍候选 → 3 层够用

关键设计点

设计为什么
节点 = 一页 16KB一次 I/O 读整页，批量过滤
数据只在叶子非叶节点更紧凑 → 树更矮
叶子双向链表范围查询直接顺序扫，不需回树
页内二分 + Page Directory槽数组加速页内定位

树高估算

假设 bigint 主键 (8B) + 指针 (6B)，每页 16KB:

非叶节点每页 key 数: 15000B ÷ 14B ≈ 1071 个
叶子每页行数 (行 ~1KB): 15 行

1 层: 15 行
2 层: 1071 × 15 ≈ 1.6 万
3 层: 1071² × 15 ≈ 1700 万  ← 千万级表高度 = 3
4 层: 1071³ × 15 ≈ 184 亿

聚簇索引 vs 二级索引

聚簇索引（主键）二级索引（普通索引）
叶子存什么完整行数据索引列 + 主键值
一个表几个1 个多个
查完整行直接返回需回表（用主键再查聚簇索引）

页分裂 — 为什么用自增主键

INSERT 自增主键: 总是在"最后一页"追加 → 只有最后一页满了才分裂
INSERT UUID: 插入位置随机 → 频繁在中间页分裂
→ 自增主键 ≈ 93% 页填充率 vs UUID ≈ 65%

4 Redis 跳表的实现原理

核心：多层有序链表，每层按概率 25% 抽节点建"高速公路"，查询 O(log N)；Redis 独创 span 字段实现 O(log N) 排名。

跳表结构

graph LR subgraph "Level 2" A2["1"] --> B2["9"] --> N2["NULL"] end subgraph "Level 1" A1["1"] --> B1["5"] --> C1["9"] --> N1["NULL"] end subgraph "Level 0 (完整链表)" A0["1"] --> B0["3"] --> C0["5"] --> D0["7"] --> E0["8"] --> F0["9"] --> G0["12"] end

查 7 的过程

Level 2: 1 → 9 (过了! >7) → 退回 1 → 降层 Level 1: 1 → 5 (≤7) → 9 (过了!) → 退回 5 → 降层 Level 0: 5 → 7 ✓ 找到！ 4 次比较 vs 原始链表 5 次。数据量上亿时受益指数级放大。

zskiplistNode 结构（Redis 源码）

typedef struct zskiplistNode {
    sds ele;                          // member 字符串
    double score;                     // 分值
    struct zskiplistNode *backward;   // 后退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 前进指针
        unsigned long span;             // 跨度 ← Redis 独有！
    } level[];
} zskiplistNode;

span：O(log N) 获取排名的秘密

Level 2: [1]──── span=3 ────→[9]── span=1 →NULL Level 1: [1]── span=1 →[5]── span=2 →[9]── span=1 →NULL Level 0: [1]→[3]→[5]→[7]→[8]→[9]→[12]→NULL 查 ZRANK(9): Level 2: 1→9, span=3 → rank = 3 (跳过了 3 个元素) Level 0: 定位到具体节点 → rank = 沿途 span 累加，O(log N)

层数随机生成

#define ZSKIPLIST_P 0.25      // Redis 选 0.25，不是标准的 0.5
#define ZSKIPLIST_MAXLEVEL 32

int zslRandomLevel(void) {
    int level = 1;
    while ((random() & 0xFFFF) < (ZSKIPLIST_P * 0xFFFF))
        level += 1;
    return min(level, ZSKIPLIST_MAXLEVEL);
}
// P=0.25 → 期望层数 = 1/(1-0.25) ≈ 1.33
// 大多数节点只有 1-2 层，内存效率高

5 如何设计一个点赞 Top 排行榜

核心：小规模 ZSet 直写 → 中规模定时批量计算 → 大规模 Kafka + Flink 流式计算。递进式架构演进 + 反作弊 + 热度衰减是加分项。

方案递进

方案一：Redis ZSet 直写（< 1 万篇文章）

// 点赞
redis.zincrby("hot:articles", 1, "article:42");

// 取 Top 100
Set<ZSetOperations.TypedTuple<String>> top =
    redis.zrevrangeWithScores("hot:articles", 0, 99);

优点：实时、代码少。缺点：大 key（几十万文章的 ZSet = 上百 MB）；zincrby 热点 key 瓶颈。

方案二：Redis 计数 + 定时批量计算（< 100 万）

6 什么情况下 MySQL 索引会失效

核心原则：索引 = B+ 树有序结构 → 一旦 MySQL 无法利用有序性定位数据区间，就是全表扫描。

8 类经典失效场景

1. 对索引列做函数/运算

-- ❌ 失效：WHERE 左边是计算结果
SELECT * FROM orders WHERE YEAR(created_at) = 2026;
SELECT * FROM users WHERE age + 1 = 19;

-- ✅ 正确：让索引列保持"干净"
SELECT * FROM orders WHERE created_at >= '2026-01-01'
                       AND created_at < '2027-01-01';

2. 隐式类型转换

-- phone 是 VARCHAR，有索引
-- ❌ 失效：数字 → MySQL 对每行做 CAST(phone AS UNSIGNED)
SELECT * FROM users WHERE phone = 13800138000;

-- ✅ 正确
SELECT * FROM users WHERE phone = '13800138000';

3. LIKE 以 % 开头

-- ❌ 失效：B+ 树按前缀有序，% 在开头无法定位起点
SELECT * FROM articles WHERE title LIKE '%Claude Code%';

-- ✅ 前缀固定可定位
SELECT * FROM articles WHERE title LIKE 'Claude Code%';

4. 联合索引不满足最左前缀

-- 索引: (a, b, c)
-- ✅ 生效: WHERE a=1 / WHERE a=1 AND b=2 / WHERE b=2 AND a=1 (优化器调序)
-- ❌ 失效: WHERE b=2 (跳过 a) / WHERE c=3 (跳过 a,b)
-- ⚠️ 部分: WHERE a>1 AND b=2 (a 范围查询后 b 只用于排序不过滤)

5. OR 中有非索引列

-- ❌ name 有索引，age 没有
SELECT * FROM users WHERE name = '张三' OR age = 25;

-- ✅ UNION 分别走各自索引
SELECT * FROM users WHERE name = '张三'
UNION
SELECT * FROM users WHERE age = 25;

6. 扫描比例过高 → 优化器放弃索引

-- 表中 99% 行 gender='男'
-- MySQL 估算回表代价 > 全表扫描代价 → 不走索引
SELECT * FROM users WHERE gender = '男';
-- 阈值经验值：扫描比例 > ~15-25%

7. != / NOT IN / NOT EXISTS

-- ❌ 否定条件无法利用有序性定位区间
SELECT * FROM users WHERE status != 'deleted';
SELECT * FROM orders WHERE id NOT IN (1, 2, 3);

8. IS NULL / IS NOT NULL

-- 老版本 MySQL：索引不存 NULL → 不走
-- 5.7+ 部分支持，取决于优化器
-- 覆盖索引 + IS NULL 通常可以走

EXPLAIN 验证

字段关注值
typeALL = 全表扫描 → const = 最佳
keyNULL = 没走索引
rows越大越差
ExtraUsing filesort（额外排序）、Using index（覆盖索引）
