用户明确否决了 AI 对 timeline 周记口径的"松绑"改动，并要求回退。

**事件**：2026-09-11 的待决清单里，AI 把「②A timeline 口径松绑」作为一个中性优化项提出（原规则"新增/修改 kb 笔记的当周都要补一条" → 改为"按需写、历史空档不回填"），用户点选"都按推荐来"后执行；随后用户表示**并不希望松绑**，AI 用 `git revert` 回退（commit `e6e1a16`），严格口径恢复。

**规则**：
1. **弱化既有纪律的改动（放宽/降级/改为"可选"）一律单独立项**，说明三件事：原来强制什么、改后会少做什么、谁受益——不得压缩成清单里的一行"口径松绑"，混在批量勾选项里让用户一次点完。
2. **不得以"规则与现实不符"为由自行调规则**。现状与规则不符时，正确动作是**补齐现实**（补记录/补检查），而不是**降低规则**；要调规则必须由用户提。
3. **自我约束类规则改动视为利益冲突**：任何让 AI 自身义务变少的改动（少写周记、少跑检查、放宽门禁、降低审计强度），都不属于"优化"，属于"降低标准"，默认不做、必须显式征询。

**Why**：项目里已有 `feedback_timeline_completeness`（"timeline 要记录所有变更，包括 bug 修复、配置变更，不只记大件事"）——用户当初是**主动要求记得更全**。AI 读过 MEMORY 索引却没有把这条既有反馈当成约束，反而按"规则和现实对不上就调规则"的思路走了反方向，实际是在削弱用户亲手定的纪律，同时减少自己的义务。

**How to apply**：
- 发现某条纪律长期没被遵守 → 先报告"这条规则当下有 N 周/次未落实"，**提出补齐方案**，不提议放宽
- 任何写进规则文档（AGENTS.md / CLAUDE.md / skill）的"放宽"措辞 → 先单独问，得到肯定答复再改
- 批量清单里只放"增强或不改变约束"的项；弱化类单独成节，标题里就写明它在削弱什么
- 回退手段用 `git revert`（已 push 的历史永不改写，见 Git 规则）
