# KB Content Style — 细节参考 (reference.md)

> 本文件是 [SKILL.md](./SKILL.md) 的细节扩充，权威入口是 SKILL.md 正文。以下为被压缩下放的具体规则全文。

## 文件拆分规则全文

**核心原则：拆分决策权归用户。AI 不擅自提案拆分，除非用户主动要求。**

### 规模信号（只关注，不触发提案）

| 维度 | 阈值 | AI 行为 |
|---|---|---|
| 行数 | >1000 | **关注**：在 self-review 或退出检查时提示用户"该文件较大（N 行）"，一句话点到为止，**不提案拆分** |
| 行数 | >1500 | 同上——不再"必须拆"，仍只是提示 |
| 章节数 | >7-8 个 `##` | 同上 |

规模大本身不是问题。一个 1200 行但主题凝聚、章节连续、结构规整的文件，是健康的知识沉淀，不该被拆散。

### 结构信号（可提案重组，但不拆分）

以下属于**结构违规**，AI 可主动提案**重组**（文件数不变，内部整理），重组也需用户确认：

- 日期戳小节（`## YYYY-MM-DD - ...`）与编号章节（`## N. ...`）混合 —— 违反"重组而非堆砌"
- 章节编号跳号（arch-lint [13/15] 会报）
- 单节过大（>400 行）且该节可独立成段
- 主题分散：3+ 个互不相关的方向堆在一个文件里

**注意**：结构违规的判定要保守。如果文件虽有轻微瑕疵但用户认为"规整"，尊重用户判断，不反复提案。

### 拆分（一个文件变多个）

**永不擅自提案。** 仅当用户主动说"拆一下""这个文件太长了拆开""把 X 部分独立出去"时才执行。

执行拆分时：
- 原文件保留核心 + 指向子文件链接
- 章节编号重新从 1 整理（无跳号）
- 更新 INDEX.md 和 overview.html
- 拆出的新文件遵循中文文件名 = frontmatter title 规则

### 判断方法

读完文件后问自己——"这个文件虽然大，但内容是否围绕一个凝聚的主题、章节是否连续规整？" **是 → 即使超阈值也不提案。否（结构散乱）→ 可提案重组，但听用户的。**

## 中文文件名细则（强制）

磁盘文件名必须与 frontmatter `title` 一致：
- 冒号 `:` → 全角 `：`
- 移除 `/ \ * ? " < > |` 非法字符
- 多空格合并为一个
- 过长（>60 字）截断

新文件创建时直接用中文名；旧文件重命名用 `node scripts/rename-mapping.js --apply`。

## 目录深度

默认两层（`技术/Java/jvm-gc.md`）。允许第三层的条件：每个子目录 ≥3 篇文件 + 子领域边界清晰。

## 同主题聚合

同主题持续追加到同一文件，不按日期拆分。文件内**最新内容追加在顶部**，以 `## YYYY-MM-DD - 标题` 为二级标题。

遇到**全新主题**时新建文件，按主题分类放入对应子目录（默认两层，见下）。

## 章节编号 + 标题 ID

- 使用 `## N.` 样式时，h2 编号必须从 1（或 0）连续递增 —— 由 `arch-lint.sh` 章节编号连续性检查自动兜底
- 内联代码不影响 slugify：`buildToc` 在 slugify 前必须 `stripInline` —— 由 `arch-lint.sh` 标题 ID 契约检查 + `tests/lib.test.js` 双保险
- 修改 lib.js slugify 或 heading renderer 时，必须同步更新 lib.js + app.js

> lint 检查逻辑见 [arch-lint-fix-guide skill](../arch-lint-fix-guide/SKILL.md)（第 12/13 项）。

## 跨文件关联细则

涉及多维度的知识点（如《我看见的世界》提到 RNN）：
- 读书笔记侧重阅读上下文 + 感悟
- 技术文件侧重纯技术干货
- **两处不是复制**，互留链接 `相关: ../技术/ai/rnn.md`（双向链接）

## 双输出原则全文（强制性）

回答用户问题时，**控制台回答**和 **KB 沉淀**是两个独立产物，必须同时提供：

### 控制台（当前对话）
- 给用户一份**直接可读的完整回答**——结构化、有深度、当场看懂
- 不能只是"我写了个文件，详见 xxx.md"或一个索引摘要
- 侧重**回答用户的问题**，语言偏对话式，可以比 KB 版简洁
- **绘图用结构化文字**（缩进列表 + 表格 + emoji 箭头 → ✅ ❌），**禁止** ASCII 框图（`┌──┐` 等 box-drawing 字符拼图）和 Mermaid 源码块——终端无法渲染

### KB 文件（长期知识库）
- 体系化归档版——更完整、有 Mermaid/表格/代码 demo、带交叉链接
- 侧重**知识的结构化沉淀**，面向未来回顾
- 可以包含控制台没提到的扩展内容
- **绘图用 Mermaid**（overview.html 渲染为 SVG）

### 执行顺序
1. **先**在控制台输出核心回答（文字直接打出来，用户立即可读）
2. **然后**做 KB 写入（工具调用写文件、commit 等）
3. 最后简短总结沉淀了什么（一两句，不需要重复内容）

### 控制台输出格式校验（强制性）

输出长篇 markdown 回答时，必须确保以下三项无误：

1. **无重复段落**：同一段内容不能出现两次。"例子 B 重复两遍"是 2026-06-07 的典型事故。
2. **所有代码块有完整围栏**：` ```mermaid `、` ```go ` 等必须成对出现，不能只写 `graph LR` 裸奔。
3. **列表/表格格式正确**：`- ` 列表项、`|` 表格行、`>` 引用块不能因换行缺失而挤压成一段。

**反面例子**：上轮会话中，Harness vs Multi-Agent 的控制台回答出现了 mermaid 图缺失代码围栏、子标题"例子 B"整段重复两次——导致用户看到的是一堆格式错乱的 raw text。

### 判断标准
- 如果用户只看控制台不翻文件，**能不能看懂答案**？→ 能 = 合格
- 如果用户只看 KB 文件不看控制台，**能不能系统回顾**？→ 能 = 合格
- 控制台输出中是否有**明显格式破损**（重复段落 / 裸奔代码 / 列表挤压）？→ 无 = 合格

## 判断标准示例

"卷积操作是通过滤波器在输入矩阵上进行滑动窗口运算提取特征" —— 这种纯定义就是太抽象（反面例子）。读起来像教科书定义 = 太抽象；读起来像有人拿草稿纸演示 = 对的。
